\subsection{Requisitos de sistema y requisitos de software}
Las normas de ciclo de vida distinguen niveles de requisitos que se derivan unos de otros: de las necesidades de los stakeholders se obtienen los requisitos del sistema y, de los que se asignan al software, los requisitos de software \cite{iso29148,iso15288,ieee12207}. Esta secci\'on define cada nivel y los ilustra con el sistema de gesti\'on con IA del restaurante El Balc\'on, de Quevedo (Los R\'ios), en adelante SGR-IA.

\subsubsection{Requisito de sistema}
\textbf{(i) Definici\'on formal.} Los requisitos de sistema describen lo que debe hacer el sistema considerado como un todo, es decir, el conjunto de hardware, software, personas y procedimientos, y con qu\'e calidad debe hacerlo; se derivan de los requisitos de los stakeholders \cite{iso29148,iso15288}.\par
\textbf{(ii) Explicaci\'on propia.} El requisito de sistema se ubica en la frontera del producto completo, sin decidir todav\'ia qu\'e parte la resuelve el software y cu\'al el hardware o las personas. Por eso suele expresarse en t\'erminos de comportamiento observable desde fuera del sistema. Esto permite que el equipo negocie con el cliente sin entrar en detalles de implementaci\'on, y que despu\'es se asigne cada requisito a un componente.\par
\textbf{(iii) Ejemplo en El Balc\'on.} Que el pedido tomado en la sala llegue a la cocina en menos de 2 segundos (RF-01) es un requisito de sistema: involucra la tablet del mesero, la red local, el servidor y la pantalla de cocina, y no solo un programa.\par

\subsubsection{Requisito de software}
\textbf{(i) Definici\'on formal.} En la norma 12207, el an\'alisis de requisitos de software transforma los requisitos del sistema asignados al elemento de software en requisitos del propio software \cite{ieee12207,iso29148}. % VERIFICAR: nombre exacto del proceso y clausula en 12207:2017
\par
\textbf{(ii) Explicaci\'on propia.} El requisito de software ya habla de lo que debe cumplir un componente de software concreto, por ejemplo su comportamiento, sus datos y sus interfaces con otros componentes. Es m\'as detallado que el de sistema y sirve de base directa para el dise\~no y las pruebas del c\'odigo. Si un requisito del sistema se reparte entre varios componentes, cada uno recibe su propio requisito de software.\par
\textbf{(iii) Ejemplo en El Balc\'on.} Para el pron\'ostico de demanda (RF-02), el requisito de software del m\'odulo de predicci\'on es leer el historial de ventas, entrenar el modelo y entregar la predicci\'on por plato. Para la impresi\'on de comandas (RI-01), el software debe generar la comanda en el formato que entiende la impresora t\'ermica.\par

\subsubsection{Derivaci\'on y trazabilidad entre niveles}
\textbf{(i) Definici\'on formal.} La trazabilidad consiste en poder seguir cada requisito hacia su origen y hacia los requisitos y elementos que se derivan de \'el; la norma 29148 la exige entre los niveles de requisitos \cite{iso29148}.\par
\textbf{(ii) Explicaci\'on propia.} Sin trazabilidad no se puede saber por qu\'e existe un requisito ni qu\'e se afecta si cambia. Cada requisito hereda su justificaci\'on del nivel superior: el de software, del de sistema; el de sistema, del de stakeholder; y este, del objetivo de negocio. Tambi\'en permite detectar requisitos sin origen y objetivos que nadie ha traducido en requisitos.\par
\textbf{(iii) Ejemplo en El Balc\'on.} La cadena es: objetivo de negocio RN-01 (reducir mermas) $\rightarrow$ requisito de sistema RF-02 (pron\'ostico semanal) $\rightarrow$ requisito de software del m\'odulo de predicci\'on, con su meta de calidad RNF-05 (error m\'aximo del pron\'ostico).
